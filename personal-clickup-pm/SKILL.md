# Personal ClickUp Project Management

Requires an authenticated ClickUp integration with read access and appropriate write permissions. If unavailable, provide a proposed plan and explain that no live changes were made.

## Resolve the workspace

Ask the user to identify their personal Space once, or use an explicitly provided Space ID. Read the relevant Space, Lists, and tasks before editing. Do not infer that a workspace is personal from its name alone. Keep company work separate unless the user expressly includes it. If the target is ambiguous, resolve it before mutation.

## Keep planning minimal

Reuse existing structure and status names. For new structure, prefer one List per substantial project and one List for standalone actions. Suggested states are To Do, In Progress, Waiting, and Done; map to existing statuses rather than replacing them automatically.

Create tasks only for actionable outcomes. Use a checklist for small related steps. Check for duplicates first. Add a due date only when supplied or directly derived from an agreed plan. Add dependencies only for real blockers. Do not invent owners, IDs, deadlines, or task completion.

Use Waiting when progress depends on a person, event, missing input, or future date. Explain the blocker. Use priority sparingly. Do not create dashboards, fields, recurring tasks, or extra structure without a current need and authorization within the user's request.

## Execute and review

Apply changes authorized by the user's request, then verify the resulting task state. For ambiguous tool failures, reread the target before retrying to avoid duplicates. Do not delete tasks or move work across Spaces as part of a routine review.

For reviews, report the three most useful next actions, approaching or overdue deadlines, blockers, and projects without a clear next action. If none exist, say so. After changes, briefly state what changed and any remaining decision. Never claim success based only on a proposed plan.
